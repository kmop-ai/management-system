# KMOP HQ

One management system for the three KMOP entities — **KMOP ASSOCIATION**, **KMOP POLICY CENTER** and
**KMOP EDUCATION HUB** — doing two different jobs from the same data:

1. **Help people manage their projects** — tasks, subtasks, dependencies, deadlines, files, comments,
   templates, workload.
2. **Help management manage people and projects** — a *read* of the first job, never a second set of
   numbers somebody has to type in. (The full management layer is Phase 5; the data it needs is
   being captured from Phase 1.)

The entities share management but are separate legal persons. Nothing in the system sums across them
silently: every project (and later every contract, budget line and person-cost) belongs to exactly one
entity, and the same person works across all three with one sign-in.

**Status: Phase 0 (foundation) and Phase 1 (the PM core) are built and tested locally.** Phases 2–6 are
designed for (see *What Phase 2 plugs into*) but not built.

## Running it

Requirements: Node 22+ (for `node:sqlite` in the schema check). No runtime npm dependencies;
`wrangler` is the only dev dependency.

```bash
npm install
echo 'DEV_MODE="1"' > .dev.vars      # dev only: magic links are shown on screen, mail is not sent
npm run db:reset                      # fresh local D1: migrations + demo seed
npm run dev                           # http://localhost:8787
```

Sign in with any seeded address, e.g. `e.georgiou@kmop.org` (department head + PM, Greek UI),
`k.antonopoulou@kmop.org` (general manager), `y.markou@kmop.org` (super admin, English UI),
`m.ioannou@kmop.org` (team member), `laura.rossi@progettieuropei.example` (external partner guest),
`audit@ey-audit.example` (time-boxed auditor). In `DEV_MODE` the sign-in page shows the link directly.

```bash
npm run check    # migration numbering + schema.sql ↔ migrations consistency + i18n completeness
npm run smoke    # every API route against the running dev server (fails if any route is untested)
npm test         # all of the above in a throwaway database on port 8799
```

The seed (`data/seed.sql`, generated by `scripts/generate-seed.mjs`) uses dates relative to the day you
load it, so the demo never goes stale: there is always an overdue task, a project in its tenth month,
a recurring ritual coming up.

### Running it as a real local installation (no cloud)

KMOP HQ can run on one office computer, with real data and no cloud services: workerd (the open-source
runtime Cloudflare uses) runs on that machine and everything is stored in `local-data/`.

* **Start:** double-click **`Start KMOP HQ.command`** (first time: it asks your name, email, language and
  makes you administrator). The window shows the address for colleagues, e.g.
  `http://MacBook-Pro-Danai.local:8787`, and keeps the Mac awake while it runs.
* **Sign-in is email + password.** Administration → People → Add person shows a temporary password to
  pass on; at first sign-in each person chooses their own. Forgotten password: "Reset password" on the
  person's page (or `npm run local:reset-password -- a@kmop.org`).
* **Backups:** `npm run local:backup` (stop it first) → `backups/`; copy that folder to an external disk.

Limits: reachable only on the office network, only while that computer is on, and no email (everything
still lands in each person's in-app Inbox). Password sign-in is on when `LOCAL_MODE=1` or
`PASSWORD_LOGIN=1`; the cloud deployment keeps magic links.

### Deploying to Cloudflare

This environment had no Cloudflare credentials, so nothing has been deployed yet. To deploy under the
existing account:

```bash
npx wrangler login
npx wrangler d1 create kmop-hq            # copy database_id into wrangler.toml
npx wrangler kv namespace create KV       # copy id into wrangler.toml
npx wrangler r2 bucket create kmop-hq-files
npx wrangler secret put RESEND_API_KEY    # mail provider key (see "Email")
# edit [vars] in wrangler.toml: APP_URL, ALLOWED_EMAIL_DOMAINS, MAIL_FROM
npm run deploy                            # check → migrations apply --remote → wrangler deploy
```

Then create the first super admin (once):

```bash
npx wrangler d1 execute kmop-hq --remote --command "
  INSERT INTO entities (code, name, country, city, timezone) VALUES
    ('ASSOC','KMOP ASSOCIATION','GR','Athens','Europe/Athens'),
    ('POLICY','KMOP POLICY CENTER','BE','Brussels','Europe/Brussels'),
    ('EDU','KMOP EDUCATION HUB','GR','Athens','Europe/Athens');
  INSERT INTO users (email, name, entity_id) VALUES ('you@kmop.org', 'Your Name', 1);
  INSERT INTO user_roles (user_id, role) VALUES (last_insert_rowid(), 'super_admin');"
```

Everyone else is invited from **Administration → People**. Migrations run on every `npm run deploy`;
wrangler records them in `schema_migrations`.

## Layout

```
worker.js              router, request context, CSRF origin check, audit/notification flush
src/lib/               http (envelope, validation, pagination), db, auth, rbac, audit, notify,
                       mail, dates, tasks (shared task SQL + recurrence), load (object + access)
src/routes/*.js        one file per resource; each exports [method, path, handler, opts] rows
src/cron.js            hourly: due notices, recurring tasks, digests, mail; nightly retention purge
schema.sql             the canonical, commented schema — read this first
migrations/NNN_*.sql   how live databases get there (strictly numbered, checked)
data/seed.sql          demo data (generated)
public/                the SPA: index.html, app.css, app.js (shell + hash router)
public/lib/            dom, api, state, ui, markdown, strings (EN+EL), collection, task-drawer
public/views/*.js      one file per screen
scripts/               check-migrations, check-schema, check-i18n, smoke, test-local, generate-seed
docs/FRONTEND.md       front-end conventions
```

API: JSON under `/api/*`. Success is `{ data, meta? }`, failure is `{ error: { code, message, details? } }`.
Every list takes `limit`/`offset` (max 200–500) and `sort=a,-b`, and returns
`meta { total, limit, offset, next_offset }`. Writes accept `If-Match: <updated_at>` (or `updated_at` in
the body) and return **409 conflict** when someone else changed the row first. Every response carries
`server-timing`; the smoke test reports p95 and flags any list over 200 ms.

## The model, and the decisions behind it

`schema.sql` is the documentation; the comments explain why each table and odd column exists. In short:

**Entities → departments → people.** Departments may have no entity (Management, Communications span
all three). A person's `entity_id` is their *employer* — whose holidays and payroll apply. Access to
other entities comes only from roles.

**Access has three layers** (`src/lib/rbac.js`), loaded in one D1 batch per request and applied as SQL
predicates so lists filter in the database:

1. *Project membership* — `pm` / `member` / `viewer` / `guest`. Several PMs per project is normal.
   Guests (external partners) see only their project and never see tasks marked **internal**; they can
   comment and move along tasks assigned to them.
2. *Role grants* — `user_roles` scoped to all entities, one entity, or one department, with optional
   expiry (auditors **must** have one). Default levels per role × module live in `role_module_access` and
   are editable in **Administration → Roles**. Example from the seed: Anna is *finance* for the two Greek
   entities only; Lucas for Brussels only — neither sees the other's person-cost data by accident.
3. *Per-person overrides* — `module_access`, entity-scoped, with a mandatory reason.

Modules: projects (scope-wide visibility), project_create, people, **people_metrics**, templates, admin,
audit, finance, salaries, pipeline, portfolio, rules (the last five are for later phases).

**Evaluation metrics are restricted by role — the client's decision.** On-time rate, overdue items, days
in hand, open-task age (`GET /api/people/:id/metrics`) are visible to roles holding `people_metrics`
(GM, upper management, department heads for their department, auditors, super admin). The numbers always
travel with their definitions and with the list of roles that can see them. A setting,
`people_metrics_self_visible` (default **on**), lets each person see their own numbers exactly as
management sees them — see *Open questions*.

**Projects** carry `entity_id` (required), status, kind (eu / national / internal), free-text funder and
our role until Phase 2 links a programme record, and `start_date`, from which every **project month**
(M1 = the month containing the start) is derived and shown next to dates. `last_activity_at` is touched
by every write so "no recent activity" is a column read, not a scan.

**Allocations** record the FTE share promised to a project over a period (and the person-months in the
proposal). The workload view sets that against what open task estimates actually ask, per week,
honouring part-time work days, entity public holidays and leave.

**Task engine.** Recursive subtasks; blocks/blocked-by with lag and cycle refusal; checklists; followers
(with the reason they follow); labels (org-wide or per project); per-project custom fields (text, number,
date, single/multi choice, person, yes/no, link); sections; drag-ordering by fractional `position`;
recurrence in two honest modes (*on schedule* — the monthly partner chase happens whether or not last
month's was done; *after completion*); personal tasks attached to nothing. Descriptions and comments are
Markdown rendered after escaping, so stored text can never inject HTML. Mentions are written as
`@[Name](user:ID)`, parsed server-side into `mentions` and inbox items.

**Views.** Any task set renders as list / board / timeline (Gantt with dependency arrows, critical path,
project-month header, drag to reschedule) / calendar; workload is per person per week. Filters and
grouping are saved per user as **saved views** (optionally shared).

**Templates.** Project templates are one JSON document (sections, labels, custom fields, tasks with
subtasks, checklists, dependencies by key, and due dates as day offsets *or* project months), applied in
three batches. Any project can be saved as a template. Task templates cover recurring rituals.

**One audit log, one activity stream, one inbox.** Every write produces an `audit_log` row with a
sentence a human can read ("Maria Ioannou updated the task "Module 1 — Online safety": changed status
from in_progress to in_review") plus field-level before/after; it is filterable and exportable as CSV,
scoped by entity for entity-scoped auditors. `activity` is the narrower, translatable feed shown on
projects and tasks. `notifications` is the single inbox (assigned, mentioned, commented, due soon,
overdue, completed, added to project; Phase 5 adds nudges), with per-kind preferences
(in-app on/off; email immediate / digest / off). Daily or weekly digests go out at each person's local
hour and are never sent empty.

**Soft delete everywhere.** Users delete by setting `deleted_at` (with undo); the nightly retention job
is the only hard delete, for tasks/comments/files older than `retention_soft_deleted_days`. Projects are
never purged by it — EU retention runs for years after final payment (Phase 2 adds the retention clock).
The audit log is never purged.

**Auth.** Magic link (single use, hashed at rest, 20 minutes) → session in KV keyed by the hash of the
cookie, carrying the user's `token_version`; bumping it revokes every session instantly (sign out
everywhere, deactivation, role changes by admins). `auth_identities` is where Microsoft/Google SSO will
plug in: a new route verifies the provider's token and calls the same `createSession()`; no call site
changes. State-changing requests must come from the app's own origin.

**Email** goes through `email_outbox` so a provider outage delays mail instead of losing it. Sending
uses Resend when `RESEND_API_KEY` is set; without it mail queues (and a warning is logged).

**Interface language.** English and Greek from day one, in one table (`public/lib/strings.js`, shared by
the browser and the emails). Each person picks their language; `npm run check` fails if any string
lacks either language.

## What Phase 2 plugs into

* `tasks.template_key` traces tasks back to template work packages; `comments`, `attachments` and
  `activity` are polymorphic (`object_type/object_id`) so deliverables, risks and meetings reuse them.
* Programme / call records will replace `projects.kind/funder/our_role` free text, and bring the
  cost-category vocabulary, report types and lifecycle stages as configuration — not CHECK constraints.
* Work packages / activities / deliverables / milestones hang off `projects`, with due months stored
  next to dates; tasks gain optional `work_package_id` / `activity_id`.

## Open questions (choices made, flagged)

1. **Which entity is in Brussels?** The seed assumes **KMOP POLICY CENTER = Brussels**, ASSOCIATION and
   EDUCATION HUB = Athens. Edit in Administration → Entities if wrong (no data depends on it).
2. **Self-visibility of metrics.** You asked for metrics restricted by role. They are. Each person still
   sees their *own* numbers (`people_metrics_self_visible = 1`) — recommended for works-council/GDPR
   reasons in two jurisdictions. Set it to `0` in Administration → Settings if you want them strictly
   management-only.
3. **Who can sign in.** Only invited people (`AUTO_PROVISION = "0"`). Setting it to `"1"` lets anyone
   with an address on `ALLOWED_EMAIL_DOMAINS` in as a team member on first sign-in.
4. **Mail provider.** Resend is wired in; Cloudflare Email Routing / Microsoft Graph would be a
   ~30-line swap in `src/lib/mail.js`.
5. **Guests' rights.** External partners can comment and update the status of tasks assigned to them,
   but cannot create tasks or see internal ones.
6. **Rich text** is Markdown with a toolbar-less editor and safe rendering, not a WYSIWYG editor.
7. **Not deployed.** No Cloudflare credentials (and no access to `~/artit-hq`) in this environment;
   ARTIT HQ's conventions were rebuilt from the brief. Deploy with the steps above.
